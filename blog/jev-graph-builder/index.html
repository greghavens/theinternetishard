Build and verify a graph with Jev Graph Builder

Walk through every stage, from approving the ontology to auditing the links the agent will follow.

Greg Havens · November 23, 2026

From knowledge graphs to Graph RAG
  1. 1. How to build a knowledge graph
  2. 2. Build and verify a graph with Jev Graph Builder
  3. 3. Put Graph RAG to work in a VCF agent

In Part 1, we defined a few concepts and followed a claim back to its source. Now put that process on rails. Jev Graph Builder uses two different jobs: a coding agent drafts text and structured proposals, and Jev answers fixed decision questions about them. Ordinary code handles jobs where the output should be deterministic, such as computing IDs, looking up a source span, or finding candidate neighbors. The split matters because a fluent extraction can still be unsupported.

Build a small graph first

Use Python 3.11 or later, a logged-in codex CLI, Docker or Podman for the local pgvector database (or your own PostgreSQL 16 with pgvector), and a TypeSafe key already set in TYPESAFE_API_KEY. Keep the key out of shell history and configuration files. Run from a new working directory with the three Relay example files saved in relay-docs/. Use non-sensitive inputs for the first run; selected content is processed by the configured model services.

python -m venv .venv
. .venv/bin/activate
python -m pip install 'jev-graph-builder==0.1.1'
jev-graph-builder --harness codex build ./relay-docs
jev-graph-builder status
jev-graph-builder search 'What must pass before Relay 2.0 receives traffic?' -k 5

The first build asks you to approve the proposed Registry. Read the proposal before accepting it. For these files, look for a vocabulary that keeps release, queue protocol, and validation procedure separate. If your graph is intended for more than this fixture, seed the first run with representative material so the Registry is not shaped by an unrepresentative corner of the corpus. The commands above follow the 0.1.1 release.

S0 · Draft and approve the Registry

The builder samples inputs across file types, sizes, and directories. The coding harness proposes the ontology, extraction notes, and initial policies. Jev checks proposed definitions against cited material and looks for overlapping relation types; ambiguous pairs can go back for clarification. The result is a proposed Registry version, not an active schema. A human reviews its scope, open decisions, and definitions before activation. This is where you catch a requires relation that accidentally includes optional recommendations.

S1 · Parse, normalize, and triage documents

Parsers turn files into structural units. Code normalizes them, records source and metadata, and assigns an ID from the source URI and normalized text. Exact copies can be linked rather than treated as independent evidence. Jev’s document triage decides what belongs in the corpus; material outside scope is parked. A new revision at the same path can replace prior derived material so the graph does not silently keep both versions as current.

S2 · Segment along the document structure

The builder groups content by heading, splitting oversized sections at structural boundaries. Chunks retain the heading path, and code creates structural links such as NEXT and IN_SECTION. Jev checks for boilerplate, topic, and potential prompt injection. That screening helps at ingestion, but retrieved text still needs to be treated as data by an agent. Retaining the heading is valuable here: a paragraph under “Before cutover” has a different purpose from the same words under “Troubleshooting.”

S3 · Extract facts, ground them, and verify them

The coding agent proposes entities, claims, summaries, and retrieval metadata from each chunk. The pipeline locates entity mentions and claim evidence in the text; ambiguous span matches can go through a separate Jev decision. Extraction checks ask whether the cited passage supports each entity or claim. Citation checks also apply to generated titles and keywords. Rejected candidates are not promoted. For example, “a 2.0 worker can read protocol 1.8” does not substantiate “all 1.8 deployments can upgrade directly.”

S4 · Embed and index the material

The builder embeds chunk text with heading context, entity mentions with descriptions, and claims as text. PostgreSQL with pgvector provides a vector index; there is also full-text indexing for literal signals such as error strings. Embedding model identity is tracked so a model change can trigger re-embedding. Search similarity is useful for finding candidates, but it does not decide whether their claims or links are valid.

S5 · Resolve aliases without merging unrelated things

Same-type normalized names can be grouped by rule. For other possible matches, code collects candidates from names, nearby embeddings, and document co-occurrence. Jev judges whether the mentions denote the same thing. The merge logic can block a proposed cluster union when a known negative decision crosses it. Jev chooses canonical names from observed forms, and the merge decisions remain traceable. Check that a spelling alias consolidates while two versions of Relay remain distinguishable.

S6 · Propose typed links, then verify them again

Code proposes chunk pairs using multiple signals: embedding neighbors, shared entities, structural proximity, and keyword hits. Jev chooses a relation from the approved vocabulary or declines the edge. An accepted semantic edge gets a second check based on claims and entities. If it fails, the edge does not enter the retrieval graph. An excess of candidates that do not fit the vocabulary can prompt a schema proposal rather than force a misleading edge type. That second check is another judgment, not independent proof of truth.

S7 · Audit the shape and verify the build

Code looks for isolated chunks, unusually connected hubs, contradictions, and suspicious relation patterns. Jev judges flagged items; the pipeline can demote an edge, requeue a pair, or leave a review item. The stage also samples decision consistency and builds communities with source-checked summaries. Finally, verification checks required decision records, edge verification, and remaining runnable work. This tells you whether the pipeline met its own checks, not whether the corpus covers every question.

Do a reader’s check before calling it done

Read status for failures, use audit graph to inspect graph shape, and rerun the same build after an interruption to resume. Then inspect three outcomes: whether the compatibility claim still has the right version, whether the cutover prerequisite points to the correct runbook, and whether the graph leaves an undocumented protocol unanswered. For a staged inspection, use jev-graph-builder --harness codex build ./relay-docs --stop-after segment, then remove the flag to continue. Compare a few expected links by hand instead of using node count as a quality score.

These implementation details come from the versioned stage code and build verification. Training-data export is a separate workflow. Part 3 covers serving and publishing the graph for an agent.
